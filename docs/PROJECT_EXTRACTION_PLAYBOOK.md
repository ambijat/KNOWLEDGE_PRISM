# Knowledge Prism Extraction Playbook

## What We Can Safely Learn From The Tweet

The tweet is not evidence for Knowledge Prism's ontology. It should not be used
to support claims about International Relations, Afghanistan, Central Asia,
geopolitics, semiotics, systems theory, or the corpus.

What it does contain is a useful operational pattern:

> When access to high-quality reasoning is available, do not spend it only on
> disposable outputs. Convert the reasoning into durable project assets that
> less capable future sessions can reuse.

For Knowledge Prism, that lesson is valuable because the project already depends
on continuity, evidence discipline, and cross-session restoration.

The safe extraction is therefore methodological, not ontological.

## The Principle To Keep

The useful principle is an irreversibility filter:

> If a weaker future session can easily recreate an output, do not prioritise it.
> Prioritise artifacts that preserve judgment, standards, verification logic, and
> project memory.

This fits Knowledge Prism very well.

The project should not merely generate impressive screens, reports, or concept
maps. It should leave behind:

- operating standards,
- verification rubrics,
- action plans,
- reusable scripts,
- ledgered decisions,
- atomised insight notes,
- human-facing explainers,
- capped goals with proof requirements.

Those artifacts preserve judgment.

## What Must Not Be Imported

To protect fidelity, do not import:

- the tweet's model-specific claims,
- pricing claims,
- benchmark claims,
- marketing claims,
- urgency language,
- business-growth framing,
- any claim about a model's capability as a project fact.

Those are outside Knowledge Prism's domain and not verified by the project.

The tweet is a prompt for project discipline, not a source for scholarly
knowledge.

## Adapted Moves For Knowledge Prism

### 1. Preserve Standards Before Producing More Outputs

The project should keep improving files that future sessions must obey:

- `PREAMBLE.md`
- `PIPELINE.md`
- `ACTION_PLAN.md`
- `VERIFICATION_RUBRIC.md`
- `RESTORE.md`
- `docs/KNOWLEDGE_PRISM_GUI_BROCHURE.md`

The quality bar should be checkable:

- Does the document distinguish clue, hypothesis, analysis, and evidence?
- Does it state what future agents should not claim?
- Does it define what done looks like?
- Does it name the next executable action?

### 2. Convert Reasoning Into A Durable Roadmap

Every major reasoning session should end with a project artifact, not only a chat
answer.

Good outputs:

- a revised action plan,
- a verification batch plan,
- a GUI brochure,
- a preamble,
- a technical handoff,
- a ledgered claim.

Weak outputs:

- impressive but unrecorded conversation,
- isolated screenshots,
- unverified concept lists,
- one-off summaries with no path into the project.

### 3. Atomise Insights Into Reusable Notes

Long reports are useful, but atomised notes are easier to retrieve.

Knowledge Prism should eventually add a small note system such as:

```text
docs/notes/
  0001-evidence-grade-rule.md
  0002-bridge-claim-is-not-evidence.md
  0003-graph-lab-as-thinking-interface.md
  0004-core-corpus-vs-owned-corpus.md
```

Each note should contain one insight, links to related files, and the evidence
status of the insight.

This would make the project easier for future sessions to inherit.

### 4. Use Goals, But Cap Them And Demand Proof

The tweet's useful operational warning is that long-running agent work must have
hard limits and visible proof.

For Knowledge Prism, any autonomous goal should include:

- the exact finish line,
- the maximum number of turns or time budget,
- the files allowed to change,
- the proof required,
- the stop condition,
- the verification command.

Example:

```text
Goal: Generate samples for the 20-item bridge pilot.
Cap: Stop after 90 minutes or after all 20 rows are attempted.
Proof: Paste counts for sampled, unreadable, missing, and blocked items.
Verification: Run project validation and ledger verification.
Do not: Promote any claim to concept_verified.
```

This protects ontology and cost discipline at the same time.

### 5. Record How Hard Problems Were Solved

When Knowledge Prism solves a non-trivial problem, the approach should be
recorded.

Good candidates:

- how bridge rows were mapped to corpus paths,
- why the GUI became a graph rather than a static cube,
- how evidence grades constrain synthesis,
- how duplicate groups should affect core-corpus counts,
- how sampled text should promote or block claims.

This can later become an `APPROACH_NOTES.md` or an atomised `docs/notes/`
folder.

The rule should be:

> A solved hard problem is incomplete until its method is recoverable.

## How This Improves The GUI

The tweet reinforces one design idea already present in `index.html`:

The GUI should not merely display knowledge. It should preserve and transmit
research judgment.

Possible GUI additions:

1. A `Standards` tab showing the red-line rules:
   - metadata is clue,
   - bridge claim is hypothesis,
   - sampled text is required,
   - ledger records promotion.

2. A `Goal Mode` panel where the user defines:
   - what they are trying to build,
   - which nodes are allowed,
   - what evidence grade is required,
   - what proof must be produced.

3. A `Learning Note` export that turns a graph session into a reusable note:
   - selected nodes,
   - generated thesis,
   - tension,
   - weak evidence,
   - next verification task.

4. A `Can a weaker session redo this?` warning:
   - if yes, keep it as a draft;
   - if no, save it as a standard, note, rubric, or ledger event.

These additions would make the GUI more faithful to the project, not less.

## How This Improves The Ontology Workflow

The ontology should not be built from impressive graph relations alone.

The extracted lesson says:

- save the reasoning,
- make standards explicit,
- make verification repeatable,
- record promotion events,
- keep future sessions able to execute without reinventing judgment.

In ontology terms:

```text
graph relation -> hypothesis
hypothesis -> sampled text task
sampled text -> claim event
claim event -> ontology edge
ontology edge -> communicable knowledge object
```

That path protects fidelity.

## Bottom Line

The meaningful extraction is this:

> Do not use strong reasoning only to make outputs. Use it to make the project
> easier to reason inside later.

For Knowledge Prism, that means preserving standards, verification logic,
project memory, and human-facing explainers while refusing to promote any idea
that has not passed the evidence gate.

That strengthens the ontology, protects fidelity, and gives the GUI a deeper
purpose: it becomes not just a beautiful graph, but a machine for turning
imagination into disciplined, recoverable knowledge.
